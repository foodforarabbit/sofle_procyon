## MEASURED live over the tunnel, 2026-09-10 — T100 @ 0x05e1

First hardware confirmation of BASELINE.md's numbers, read from the sensor
rather than from source:

| param | off | value | driver default | note |
|---|---|---|---|---|
| gain | 28 | 10 | — | raise to make headroom for a higher threshold |
| tchthr | 30 | 20 | — | procyon README says raise it |
| tchhyst | 31 | 10 | — | |
| movfilter | 44 | **0** | — | no sensor-side movement filter at all |
| movsmooth | 45 | **0** | — | no sensor-side smoothing at all |
| movpred | 46 | 0 | — | |
| movhysti | 47 | 10 | — | initial-move hysteresis |
| movhystn | 49 | **16** | **4** | **4x the driver default — CONFIRMED on hardware** |

raw T100+28..50: `0a 00 14 0a 0a 00 00 05 14 0a 00 02 04 02 00 00 00 00 00 0a 00 10 00`

**This is a coherent story for S1 and S3 and it was not visible from source.**
The sensor is doing NO movement filtering (movfilter=0, movsmooth=0) while
carrying a large next-move hysteresis (16 vs default 4). Unfiltered raw signal
explains jitter; oversized hysteresis explains stick-then-jump. They are
independent knobs, so they can be bracketed separately.

Order to try, unchanged from PLAN.md but now with live values in hand:
movhystn 16 -> 8 -> 4, one at a time, before touching anything else.

## UPSTREAM BUG FOUND — debug-protocol register addresses are byte-swapped

MEASURED. A read at address 0 works; a read at ANY non-zero address returns
all zeros with status OK. Address 0 is the one byte-order-agnostic value, which
is what gave it away.

`maxtouch.c:643` builds `read_address = (data[1] << 8) | data[2]` and passes it
straight to `i2c_read_register16`, while the SAME FILE at `:220` wraps its
address in `SWAP_BYTES()` for the identical call during init. maXTouch wants
the register pointer little-endian; `i2c_read_register16` transmits big-endian.
The debug read path omits the swap; the write path at `:660` has it too.

Our keymap tunnel copied that handler faithfully and inherited the bug, so this
is upstream's, not ours. Worked around host-side in `debug/mxt.py` (a probe that
detects the convention per run, so it keeps working when the firmware is fixed),
which costs zero flashes. Fix it firmware-side at flash 2.

**This is the second upstream finding on this branch**, alongside the
bounds-check in `debug/upstream-pr/`. Both belong in the same PR to
george-norton, and this one is more serious: it makes the debug protocol's
read/write unusable for every address except 0.
