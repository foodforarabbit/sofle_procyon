# Session 2026-09-10-04 — FLASH 3

## Hypothesis
Flash 2's `TAP_DISTANCE` 50→25 was wrong on both counts and this reverts it,
then fixes the symptom it was chasing at the right layer.

**What went wrong.** I changed `TAP_DISTANCE` to shorten the two-finger-scroll
dead zone. It targeted the wrong branch — the gate is `Down`, not `Tapped` — and
50 was not arbitrary. MEASURED: Ryan's taps drift 28-66 accumulated units over
53-82ms, and at 25, **6 of 8 logged contacts emitted movement instead of
clicking**. Roughly half his taps silently failed, which he reported as the tap
feeling "laggy". It was not latency; it was retries.

**The real tension.** `TAP_DISTANCE` serves two unrelated jobs: how far a
contact may drift and still count as a tap, and how far two fingers must travel
before scrolling starts. Large = reliable taps, slow scroll onset. Small = fast
onset, dropped taps. No single value satisfies both, which is why every
config-only attempt traded one symptom for the other.

**Prediction:** decoupling them in the driver gives both. Two fingers landing is
unambiguously a scroll, so it should not have to pass the tap-rejection tests at
all. With that, `TAP_DISTANCE 50` restores tapping AND scroll onset becomes
immediate.

## Changes

### vial-qmk — the fork's FIRST and only change, with Ryan's explicit approval
Branch `procyon-tap-scroll-fix`, commit `c75b4edb06`, 26 lines in
`quantum/digitizer_mouse_fallback.c`. `vial-procyon` remains pristine.

1. `Down` handles `contacts >= 2` before the tap-rejection tests → straight to
   `MoveScroll`. Removes the tension rather than trading against it.
2. `MoveScroll`/`Drag` skip the frame where `contacts != last_contacts`. On any
   contact-count change, `x`/`y` jump between one finger's position and a
   multi-finger centroid; `last_x`/`last_y` update unconditionally every call and
   never reset, so differencing across the transition emitted that jump as a
   large bogus delta. This is Ryan's "considers it a continuation of my first
   finger movement".

Both are genuinely upstream defects and belong in the george-norton PR
alongside the two byte-order bugs.

### keymap
- `DIGITIZER_MOUSE_TAP_DISTANCE` back to **50**. Now serves only tap
  classification, which is the one job it can do.
- `TAP_DETECTION_TIMEOUT` stays 120 (driver default 200). With the driver fix it
  no longer gates two-finger scroll, so it only sets tap-click latency and
  single-finger move onset — lower is better for both.

### docs
`START-HERE.md` and `PLAN.md` updated for the new build branch. This is the
exact class of stale claim that already cost a debugging cycle on this branch,
so it was fixed in the same commit rather than left for later.
