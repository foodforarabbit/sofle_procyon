# Session 2026-09-10-06 — settling out

## Where this landed
Flashes 5 and 6 walked back most of flashes 3-4. Final firmware `9a6f034b`.

## What is FIXED and verified
| symptom | fix | how it survives a power cycle |
|---|---|---|
| S1 jitter (quantised 17-unit dumps) | `movhystn` 16 -> 4 | applied from `keyboard_post_init_user` over i2c at every boot |
| S3 stick-then-jump | same mechanism | same |
| vertical worse than horizontal | `slow_limit` 12 -> 20 | compiled default |
| pointer too fast / scroll too fast | `spd` 60, `scr` 100 | compiled defaults |
| Vial layout wiped every flash | `BUILD_ID` pinned to `0x50F1E1` | `debug/build.sh` exports `VIAL_BUILD_ID` |
| tap click slow | `TAP_DETECTION_TIMEOUT` 200 -> 120 | compiled |

Ryan confirms single tap, double tap, and tap-retap-drag all work well.

## What I BROKE and had to revert
Flash 3 patched `digitizer_mouse_fallback.c` to send `contacts >= 2` straight to
`MoveScroll`, on a premise I asserted without checking: "two fingers landing is
unambiguously a scroll, never a tap." Two-finger tap for right-click IS a
two-finger tap. It stopped working entirely.

Flash 4 tried to fix it with a separate `MULTI_SCROLL_DISTANCE` threshold. Also
wrong: MEASURED, 12 of 15 two-finger contacts reached the tap path and still did
not fire `button2`, so the threshold was never the cause. I had been tuning a
number unrelated to the symptom.

Flashes 5-6 reverted both driver commits and every gesture override. The fork's
net footprint is now `util/build_id.py` alone.

Accepted trade: two-finger scroll onset returns to bimodal, lagging ~30% of
gestures by 100ms+. Ryan called that state "feels good".

## A mechanism I attributed to the wrong cause
I blamed the layout wipes on `BUILD_ID` alone. Ryan spotted the other half:
there is no `EE_HANDS` and no EEPROM mirroring in `split_common`, so **each half
has its OWN EEPROM and VIA/Vial only writes to the USB-master half**. Restoring
a layout while attached to the left half writes it to the left's EEPROM;
attaching via the right then shows the right's, which reads as a reset.

So there were two independent stores the whole time. `BUILD_ID` was genuinely
randomising every build and pinning it was a real fix, but it was not the only
reason the layout kept "disappearing". Practical rule: pick one master half and
restore the layout while attached to it.

## Still open, deliberately not chased
- **S2 liftoff drift.** 10 of 28 lifts spike 3-8x a normal frame. The 1-frame
  holdback (`LIFT`, default off) is measurably the wrong shape -- the peak is not
  always the final frame. Needs an N-frame or sensor-side fix.
- **The "ledge".** Piecewise curve steps marginal gain 30% -> 84% at
  `slow_limit`. A continuous curve shipped as `CRV`, default off, never tested.
- **Slow-movement jitter.** Not eliminated, only reduced. The directional gate
  built in flash 2 is still ON and was never A/B tested against `DIRG` off.
- **Scroll onset.** Bimodal, ~30% lag. Fixable only in the driver, and the two
  attempts to do that cost more than they bought.

## Lessons this cost real time
1. **Do not assert a gesture does not exist.** "Two fingers is never a tap" was
   wrong, cost two flashes, and broke a working feature. Enumerate what a user
   actually does before removing a code path that distinguishes cases.
2. **A measurement that does not contain the failing case proves nothing.** I
   measured scroll onset, concluded the threshold was the problem, and proposed a
   debounce -- while two-finger tap, the thing actually broken, was absent from
   the data.
3. **Read the field indices.** One analysis summed the post-gate `g` columns and
   labelled them `h/v`, producing a confident and completely wrong conclusion
   about centroid drift.
4. **Use the repo's own build script.** `debug/build.sh` existed all along,
   guards four specific failure modes, and I hand-rolled `make` for the entire
   session -- then hit the exact branch confusion it was written to prevent.
