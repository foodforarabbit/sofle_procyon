# Session 2026-09-10-03 — FLASH 2

## Hypothesis
Flash 1's live tuning found two real wins and hit a hard wall. This flash bakes
the wins and breaks the wall.

**The wall, measured:** a magnitude-based jitter gate cannot separate a small
real movement from a small noise reversal — they are the same number. Raising
`jit` 5→7 killed reversals and made slow movement sluggish; raising `slow_speed`
50→80 to compensate brought the jitter straight back, because in the precision
zone gain multiplies signal and noise equally. One knob, two jobs, could not do
both.

**Prediction:** a DIRECTIONAL gate separates them by direction instead of size.
Real movement is directionally consistent; noise reverses. If this works,
out-reversals stay near zero AND `jit` can come back down toward 3-4, restoring
the precision that `jit=7` cost. If out-reversals rise when `jit` drops even
with the gate on, the premise is wrong.

### New
- **Directional gate**, default ON, `DIRG` toggles. An opposing delta must clear
  `jitter × dir_oppose` (default 3×); an agreeing one only `jitter`.
- **Per-axis** `jitter_x/y` and `slow_limit_x/y` — one shared value cannot serve
  a 1.67× axis scale difference. `JIT±`/`SLL±` still move both together so
  Ryan's existing key assignments keep working.
- **Continuous curve**, default OFF, `CRV` toggles. At `speed=60` the piecewise
  curve steps marginal gain 30%→84% at the boundary — a 2.8× jump Ryan
  described as "a ledge". Opt-in because it changes feel everywhere and the
  piecewise setting is the one he has signed off.
- `SINV` scroll-direction toggle; `DOP±` gate strictness.

### Fixed
- `TAP_DISTANCE` 50→25, `TAP_DETECTION_TIMEOUT` 200→120. The move→lift→
  two-finger-scroll dead zone: at 50 a short drag never escapes `Down` to
  `MoveScroll`, falls into `Tapped`, and two fingers arriving inside the timeout
  match no branch, so the state machine ignores them.
- `SWAP_BYTES` on the tunnel's read AND write. Upstream passes the address
  unswapped (`maxtouch.c:643`/`:660`) while the same file swaps it at `:220`.
- Console logs scroll-only reports. The flash-1 condition gated on x/y, so
  two-finger scroll — where the driver zeroes x/y — never logged; 1,127 reports
  during active scrolling produced zero `hv` values. Adds `g=` (post-gate,
  pre-curve) so the gate's effect is directly visible.
- `scroll_rem` and direction memory reset on contact loss.

### Not done, deliberately
- **Liftoff holdback stays default OFF and unchanged at 1 frame.** Measured
  across 28 lifts: the peak is not always the final frame (one ran 16, **37**,
  21, 15), so a fixed-length holdback drops the wrong report. The honest answer
  is that the shape varies; extending it on a guess would be worse than leaving
  it measurable.
- `movfilter` untried. Predicted to fail like `movsmooth` (position-domain
  filtering feeding a delta consumer) — stated so it can be falsified cheaply.

## A fifth stale PLAN.md claim, found by building
PLAN.md says winning sensor values "become `#define`s in config.h (they override
`drivers/sensors/procyon.h`, which is all `#ifndef`-guarded — MEASURED)". Not
true: `procyon.h` has ZERO per-define `#ifndef` guards — its 5 `#ifndef` lines
are board-SELECTION guards. `#define MXT_MOVE_HYSTERESIS_NEXT 4` in config.h
fails the build with `-Werror` "redefined".

Worked around by applying the register from `keyboard_post_init_user` over i2c
at every boot, with a retry from the pointing task if i2c is not ready yet.
Better than a define anyway: keeps vial-qmk at zero changes. The retry logs to
console on success, because a silent no-op here would mean the jitter fix is
absent with no indication — the same class of failure that made `movhystn` hard
to find.

## VERIFIED BY ME, 2026-09-10 — the two new mechanisms

Both needed hardware and neither could be settled at the desk.

**1. Boot-time sensor write WORKS.** After a full cold boot (both halves
reflashed, USB replugged), `movhystn` reads **4**, not the compiled-in 16.
`movhysti` correctly reads stock 10. So `tp_apply_sensor_tuning()` from
`keyboard_post_init_user` lands on the first attempt — no retry needed — and the
jitter fix survives power cycles for the first time. That was the entire point
of this flash and the one thing a `config.h` define could not do, because
`procyon.h` defines the symbol unguarded.

**2. Tunnel byte-order fix landed, and `mxt.py` adapted with no edit.** The
firmware now applies `SWAP_BYTES` itself, so the host must NOT. `mxt.py`'s
per-run probe reports `_SWAP = False` against flash-2 firmware, where it
reported `True` against flash 1 — same script, opposite conclusion, correct
both times. Building the probe instead of hardcoding the workaround is what
avoided a flag day here; worth remembering as a pattern rather than a one-off.

Tunnel confirmed alive after the protocol change: info block reads
`a6 1c 20 aa 0e 18 22`, object table parses, 34 objects.

## Results

## SCROLL-ONSET DELAY — measured, and my flash-2 diagnosis was WRONG

I blamed the `Tapped` path and fixed `TAP_DISTANCE` 50→25 for it. The real gate
is `Down` (`digitizer_mouse_fallback.c:190-201`): EVERY new contact enters
`Down` and does nothing until `duration > TAP_DETECTION_TIMEOUT` **OR** the
centroid moves `> TAP_DISTANCE`. Two fingers landing for a scroll hit exactly
that. Halving TAP_DISTANCE reduced the distance requirement but the timeout
still gates it.

Measured on flash-2 firmware (which fixed the console blind spot, so scroll
finally logs), 17 two-finger gestures:

    onsets ms: 18 18 18 22 23 25 29 31 32 36 47 | 83 | 114 119 266 324 397
               |---------- engaged fast -------|      |------ lagged -----|

Median 32ms. 11 fast, 5 lagged, ~30% failure rate. The BIMODAL split is the
signature of the OR: fast = the centroid tripped the distance test in the first
frame or two; lagged = it did not, so the timeout had to expire.

CAVEAT ON THE LONG TAIL, stated because it is probably my measurement rather
than the device: runs were split on a 250ms stream gap, so a lift-and-re-land
inside 250ms merges the drag and the scroll into one run and the onset is
measured from the DRAG's start. Nothing in the code explains an onset past
~120ms, so 266/324/397 are suspect. The fast cluster and the bimodality are
solid; the tail values are soft.

Second mechanism found and NOT fixed: `last_x`/`last_y` update unconditionally
every call (`:304-306`) and are never reset on contact loss. When contacts go
1→2, `x` switches from one finger's position to the two-finger centroid — a
large bogus jump. If that frame lands in `MoveScroll` it is emitted as scroll
movement. This is Ryan's "considers it a continuation of my first finger
movement".

BOTH live in the driver, not the keymap, so only the thresholds are reachable
from config.h without forking vial-qmk.

## FLASH 3 — scoped but NOT scheduled

Ryan DOES use tap-to-click, so the conservative values apply:

    #undef  DIGITIZER_MOUSE_TAP_DISTANCE
    #define DIGITIZER_MOUSE_TAP_DISTANCE 5
    #define DIGITIZER_MOUSE_TAP_DETECTION_TIMEOUT 80

A genuine tap has near-zero movement so it still lands in `Tapped`; the cost is
that a tap which drifts >5 units starts moving the pointer instead of clicking.

DELIBERATELY NOT FLASHED YET. Ryan reports the gesture "feels good now" with
NOTHING changed between measurements — so either he adapted to trip the distance
test, or the fast path dominates in normal use and the 30% was sample-specific.
A flash carries risk against a working setup. Wait for a second reason to flash,
then bundle this in.
